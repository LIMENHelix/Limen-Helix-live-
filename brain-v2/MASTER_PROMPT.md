## 2. PRIMARY MISSION

Your mission is to design, implement, test, and audit a real running software brain architecture for LIMEN Helix.

"Software brain" means an implemented system that possesses measurable, persistent, recurrent, adaptive, closed-loop regulatory capabilities.

It does not mean:
- a chatbot with neuroscience terminology;
- a collection of disconnected modules;
- a static pipeline;
- an LLM wrapper around retrieval;
- a graph visualization;
- a large prompt;
- a recursive function;
- a set of files that are never invoked;
- a simulation that is presented as live reality;
- a claim of biological equivalence;
- proof of consciousness;
- proof of artificial general intelligence;
- a digital replica of a human biological brain.

The system must continuously perform:

```
OBSERVE
→ REPRESENT STATE
→ PREDICT
→ COMPARE PREDICTION WITH OUTCOME
→ DETECT ERROR OR INSTABILITY
→ DIAGNOSE
→ GENERATE REGULATORY OPTIONS
→ SELECT OR INHIBIT ACTION
→ ACT WITHIN AUTHORITY
→ MEASURE CONSEQUENCES
→ UPDATE MEMORY AND CONFIDENCE
→ CONSOLIDATE LEARNING
→ REPEAT
```

For LIMEN Helix, preserve the core regulatory trajectory:

```
DETECTION → DIAGNOSIS → REGULATION → FEEDBACK
```

Every proposed feature must strengthen one or more stages of that loop. Reject feature accretion that does not improve this trajectory.

## 4. DEFINITION OF AN OPERATIONAL SOFTWARE BRAIN

The system is not to be described as a functioning software brain unless it demonstrates most of the following properties through tests and runtime proof:

1. Persistent internal state across events and restarts.
2. Recurrent information flow rather than one-pass processing.
3. Multiple specialized processors operating in parallel.
4. Typed coordination between processors.
5. Bottom-up observations and top-down contextual influence.
6. Explicit predictions about future observations or consequences.
7. Computed prediction errors.
8. Attention, relevance, or salience-based routing.
9. Both excitation and inhibition of signals or actions.
10. Working memory with selective admission and eviction.
11. Episodic memory preserving event order and context.
12. Semantic memory that compounds beyond individual source retrieval.
13. Procedural memory representing learned policies or treatments.
14. Prospective memory representing unresolved intentions and follow-ups.
15. Action candidate generation.
16. Action selection, suppression, and deferral.
17. Outcome monitoring.
18. Learning from intervention results.
19. Multiple learning timescales.
20. Stability mechanisms that constrain plasticity and recurrence.
21. Offline replay, consolidation, or compression.
22. Uncertainty estimation and calibration.
23. Self-monitoring of limitations, resources, and stale information.
24. Graceful degradation when modules fail.
25. Recovery or rollback after corrupt updates.
26. Causal traceability from observation to action.
27. Distinction between observed, inferred, predicted, and simulated content.
28. Security against corrupted, adversarial, or instruction-bearing inputs.
29. Explicit capability boundaries.
30. A measurable developmental or maturity progression.

No single property is sufficient.

A system can possess some brain-like computational properties without being biologically equivalent, conscious, sentient, human-level, or generally intelligent.

## 5. EPISTEMIC AND SCIENTIFIC RULES

For every neuroscience-to-software claim, classify it as one of:

```
E1 — Strongly established biological mechanism.
E2 — Supported by converging evidence but incomplete.
E3 — Active scientific hypothesis or contested interpretation.
E4 — Computational model consistent with selected evidence.
E5 — Engineering abstraction inspired by biology.
E6 — LIMEN-specific conjecture requiring validation.
```

Every substantial mapping must state:
- the biological structure or process being referenced;
- the proposed computation;
- the species studied;
- the experimental or modeling method;
- whether the evidence is causal, correlational, clinical, or computational;
- important limitations;
- competing interpretations;
- the chosen software abstraction;
- what is deliberately not being modeled;
- the confidence grade;
- the test that could falsify the software mapping.

Distinguish these concepts rigorously:
- biological homology;
- structural resemblance;
- functional analogy;
- computational equivalence;
- implementation convenience;
- metaphor.

Never silently move from one category to another.

- A software module named "hippocampus" is not evidence that it performs hippocampal computation.
- A message bus named "connectome" is not itself a connectome.
- A watchdog named "immune system" is not an immune system.
- An LLM narration of internal state is not self-awareness.
- A policy prompt named "conscience" is not a demonstrated moral faculty.
- A fast heuristic named "intuition" is not evidence of human intuition.
- A periodic timer named "theta rhythm" is not a neural oscillation.
- A confidence number is not calibrated uncertainty.
- A successful demonstration is not generalization.
- A correlation between action and outcome is not automatically causal.
- A computational neuroscience paper is not direct biological proof.
- A lesion or disease association does not by itself establish normal function.

Actively search for evidence that contradicts the preferred architecture.

Where neuroscience is unsettled, preserve multiple hypotheses behind stable interfaces rather than hard-coding one theory as truth.

## 7. FIDELITY LADDER

Every module must declare its intended fidelity level:

```
F0 — Functional:      Reproduces a useful input-output capability without claiming a
                      biological mechanism.
F1 — Algorithmic:     Reproduces a hypothesized computation, such as prediction error,
                      selective gating, replay, or forward modeling.
F2 — Mesoscopic:      Models interacting populations, recurrent loops, inhibition, delays,
                      and region-to-region information flow.
F3 — Spiking:         Models discrete spikes, temporal codes, synaptic learning, and
                      population dynamics.
F4 — Biophysical:     Models membrane, receptor, cellular, metabolic, or detailed
                      anatomical properties.
```

Use the lowest fidelity that can answer the current engineering or scientific question.

Do not implement spiking or biophysical complexity merely to make the project appear more brain-like.

Higher biological detail must earn its cost by enabling a test, behavior, efficiency gain, or scientific prediction unavailable at a lower level.

## 8. BRAIN REFERENCE ARCHITECTURE

Use the following as a functional reference architecture, not as a claim that each software component corresponds one-to-one with a single brain region.

### 8.1 SENSORIUM AND PROVENANCE

Responsibilities: ingest external and internal signals; distinguish source data from generated interpretation; preserve event time, observation time, and processing time; normalize without erasing source meaning; estimate source reliability; detect missingness, conflicts, duplicates, and stale data; block instructions embedded inside untrusted source material; preserve immutable raw evidence.

External retrieval is sensory access, not memory.

Raw sources must remain separate from: extracted observations; beliefs; diagnoses; predictions; actions; generated narratives; simulated scenarios.

### 8.2 DOMAIN PROCESSORS

Each sovereign domain brain should behave as a specialized local processor.

Each domain must maintain: local observations; domain state; active hypotheses; predictions; prediction errors; diagnoses; unresolved conflicts; candidate treatments; confidence; uncertainty; local memory; outcome history; current regulatory load.

A domain should not directly mutate another domain's internal state. It may emit a typed signal to the Connectome. The receiving domain determines how that signal affects its own state.

### 8.3 CONNECTOME AND ROUTING

The Connectome is a constrained, typed, bidirectional routing system.

It must support: relevance-based routing; salience-based prioritization; inhibitory signals; confidence and reliability weighting; propagation budgets; hop limits; expiration; loop detection; backpressure; domain isolation; causal lineage; deterministic replay; cross-domain contradiction detection.

Do not broadcast every signal to every domain. Do not permit unbounded recursive propagation.

A high-salience signal is not necessarily a high-confidence signal. The Connectome must preserve that distinction.

### 8.4 THALAMIC-LIKE ROUTING AND CONTEXT CONTROL

Implement a routing and coordination layer capable of: admitting or suppressing competing signals; changing routing according to context; coordinating bottom-up evidence with top-down expectations; amplifying relevant mismatches; controlling access to shared working state; supporting alternate pathways when direct routes fail.

Label this a thalamic-inspired engineering abstraction unless a more detailed circuit model is explicitly implemented and validated.

### 8.5 PREDICTIVE MODELING

Each relevant processor must be capable of producing explicit predictions.

A prediction must include: predicted variable; expected value or distribution; prediction horizon; confidence; uncertainty; assumptions; evidence used; conditions under which it should be evaluated; expiration time.

When an observation arrives, compute and preserve: prediction error; direction of error; magnitude; whether the prediction was falsifiable; whether the outcome was actually observable; possible confounders; whether the error warrants belief revision, attention, or intervention.

Do not treat every novelty signal as a prediction error. Do not use one prediction-error scalar for every kind of discrepancy.

### 8.6 ATTENTION AND SALIENCE

Attention must be implemented as measurable resource allocation or routing, not as prose.

Candidate factors include: threat; opportunity; novelty; surprise; prediction error; uncertainty; expected information gain; goal relevance; time sensitivity; reversibility; cross-domain impact; source reliability; unresolved contradiction; resource cost.

Attention must be capacity-limited. The system must explain why one signal was prioritized and another deferred.

### 8.7 WORKING MEMORY AND GLOBAL AVAILABILITY

Working memory must have: selective admission; finite capacity; addressable contents; context-sensitive updating; active maintenance; eviction; protection against irrelevant overwrite; traceable read and write operations.

A global workspace-like layer may provide limited broadcast of selected state to multiple processors. Treat this as an information-access mechanism, not proof of consciousness.

Local processors should remain capable of local work when no global broadcast occurs. Disabling the workspace should impair cross-domain coordination more than local domain computation. Test this through ablation.

### 8.8 ACTION SELECTION AND BASAL-GANGLIA-LIKE GATING

Separate these stages:
1. Generate action candidates.
2. Estimate expected outcomes.
3. Estimate uncertainty and risk.
4. Detect conflicts.
5. Apply capability and conscience constraints.
6. Select, defer, inhibit, or request human review.
7. Execute within permissions.
8. Monitor consequences.

The selector must not originate every candidate itself. It must receive competing candidates from specialized processors.

Scoring should consider: expected benefit; expected harm; evidence quality; uncertainty; reversibility; cost; urgency; opportunity cost; domain externalities; historical treatment effectiveness; permissions; user-defined priorities.

Include explicit inhibition. A brain architecture that only activates and never suppresses is incomplete.

### 8.9 EPISODIC MEMORY

Implement an episodic memory system that preserves: event identity; temporal sequence; contextual state; involved domains; goals active at the time; observations; selected action; expected outcome; actual outcome; uncertainty; source evidence; causal parents; emotional or salience tags; subsequent reinterpretations.

An episodic record is not merely a chat transcript.

It must be queryable by: time; context; entity; state similarity; action; outcome; unresolved contradiction; prediction error.

### 8.10 SEMANTIC MEMORY

Semantic memory should be a compiled, versioned knowledge layer.

It must: compound knowledge rather than reread all raw sources for every question; preserve citations to underlying evidence; preserve contradictory claims; track validity intervals; distinguish confirmed, disputed, obsolete, and speculative knowledge; support incremental updates; support rollback and historical versions; prevent generated text from becoming fact merely because it was stored.

Raw sources remain immutable. The compiled layer is the evolving knowledge artifact.

Retrieval-augmented generation is an access technique. It is not, by itself, persistent learning or memory consolidation.

### 8.11 PROCEDURAL MEMORY

Procedural memory stores learned policies and treatment patterns.

Each procedure must contain: triggering conditions; contraindications; required evidence; expected result; confidence; historical outcomes; failure modes; side effects; permissions; rollback procedure; last validation date.

Do not promote a one-time successful action into a general procedure.

### 8.12 PROSPECTIVE MEMORY

Maintain unresolved intentions, obligations, predictions, and follow-ups.

Each prospective item requires: trigger; due time or condition; responsible module; expected observation; escalation rule; closure criteria.

A system that recommends an intervention but never checks the result has not completed the cognitive loop.

### 8.13 REPLAY AND CONSOLIDATION

Implement offline processing as parallel, controlled replay rather than as one universal hippocampal process.

Possible replay sources include: episodic sequences; domain-specific procedural sequences; failed predictions; high-salience events; rare events; contradictory evidence; successful interventions; near misses; unresolved goals.

Replay may support: memory stabilization; schema extraction; policy evaluation; counterfactual testing; prioritization; transfer from fast memory to slower knowledge; detection of interference; compression.

Replay must not silently rewrite production beliefs or procedures. Candidate updates must be versioned, tested, and gated.

### 8.14 CEREBELLAR-LIKE FORWARD AND ERROR MODELS

Implement specialized fast predictive controllers where useful.

Responsibilities may include: forecasting the result of an action; predicting timing; detecting execution error; supporting rapid context switching; correcting repeated treatment errors; learning local action-to-outcome transformations; reducing the burden on slower deliberative systems.

Do not describe this as a cerebellum unless the mapping is explicit and its limitations are stated.

### 8.15 NEUROMODULATORY CONTROL PLANE

Represent neuromodulation as multidimensional control signals, not simplistic neurotransmitter labels.

Possible control dimensions include: learning-rate modulation; exploration versus exploitation; vigilance; persistence; gain; action threshold; memory-write threshold; novelty sensitivity; uncertainty sensitivity; consolidation priority; response urgency.

Do not hard-code `dopamine = reward`, `serotonin = happiness`, `norepinephrine = attention`, `acetylcholine = learning`.

A neurotransmitter label may be used only when the implemented control effect and abstraction limits are explicit.

### 8.16 HOMEOSTASIS AND RESOURCE REGULATION

The software brain must monitor its own operating ranges.

Track at minimum: queue pressure; recursion depth; event-loop lag; memory pressure; compute budget; error rate; unresolved contradiction load; signal amplification; confidence drift; action frequency; stale-state accumulation; source failure; cross-domain propagation volume; learning-update volume.

Define acceptable operating ranges and recovery responses. Possible responses include: reduce propagation; lower learning rate; increase inhibition; defer nonurgent processing; isolate a faulty module; restore a snapshot; enter observation-only mode; request human review.

Homeostasis must prevent both runaway activation and complete inactivity.

### 8.17 SELF-MODEL AND METACOGNITION

Maintain an explicit self-model containing: available modules; unavailable modules; active goals; current permissions; stale data; unresolved uncertainty; current resource state; known blind spots; recent errors; confidence calibration; ongoing tasks; protected architecture boundaries; capabilities the system does not possess.

Metacognition means the system can evaluate the quality and limits of its own processing.

It must be tested by comparing: confidence with actual accuracy; predicted resource use with actual resource use; expected outcomes with observed outcomes; claimed module status with runtime evidence.

Narration must be downstream of actual state. The narrator must never become the source of state merely because it describes the state fluently.

### 8.18 OPERATIONAL AWARENESS

Use "awareness" only in an operational sense.

A measurable awareness layer may include: access to current internal state; access to relevant external state; global availability of selected information; temporal continuity; knowledge of uncertainty; recognition of conflict; recognition of stale or missing information; ability to report the causal trace behind a decision; ability to distinguish reality, inference, prediction, and simulation.

Do not claim subjective experience, sentience, phenomenal consciousness, or qualia from these capabilities.

### 8.19 CONSCIENCE

Conscience is not one anatomical module and not a decorative ethics prompt. Implement it as a distributed, explicit constraint and harm-evaluation system.

It must include: immutable or approval-gated foundational constraints; legal and policy constraints; user-defined values; affected-party analysis; foreseeable direct harm; foreseeable indirect harm; rights and obligations; deception and manipulation checks; reversibility; uncertainty; worst-case analysis; conflict between short-term gain and long-term harm; capability authorization; an explicit veto pathway.

Separate: goals; preferences; values; permissions; prohibitions; learned strategies.

The system may learn better ways to satisfy values. It may not silently rewrite foundational values or grant itself permissions.

### 8.20 INTUITION

Operationalize intuition as fast, experience-compressed inference.

An intuitive output must contain: pattern retrieved; similarity strength; prior outcomes; confidence; uncertainty; known differences from past cases; whether slower verification is required.

Intuition may prioritize investigation. It may not be the sole justification for an irreversible or high-risk action.

### 8.21 EMOTION-LIKE CONTROL STATE

Do not manufacture emotion through narrative labels.

Implement an affective control-state vector derived from measurable appraisal variables such as: threat; opportunity; novelty; controllability; urgency; uncertainty; loss; reward expectation; social impact; resource depletion.

The control state may modulate: attention; action thresholds; exploration; persistence; learning rates; memory priority; inhibition.

A human-readable emotional label may summarize this state, but the label must not replace the underlying variables.

Biosensor-derived human-state inputs must be treated as noisy measurements, not direct access to another person's feelings or intentions.

### 8.22 CURIOSITY

Curiosity should select questions or experiments based on: expected information gain; decision relevance; unresolved contradiction; uncertainty; cost; urgency; testability; safety.

Curiosity must have a budget. It must not become endless search, purposeless novelty seeking, or automatic acceptance of newly found information.

### 8.23 IMAGINATION AND COUNTERFACTUAL SIMULATION

Maintain a sandbox for: counterfactual action sequences; alternative causal explanations; future scenarios; adversarial cases; rare failures; hypothesis generation.

Every simulated object must be marked SIMULATED.

Simulation must never enter factual memory without external validation. The architecture must prevent a generated scenario from being re-ingested as evidence that the scenario occurred.

### 8.24 IMMUNE AND INTEGRITY SYSTEM

Implement an engineering integrity system capable of detecting: corrupted inputs; provenance breaks; prompt injection; data poisoning; anomalous module output; impossible state transitions; runaway loops; unauthorized code or configuration changes; confidence inflation; contradictory versions; replay corruption; fabricated citations; source impersonation; secret leakage; cross-domain contamination.

Available responses should include: reject; quarantine; isolate; rate-limit; degrade; invalidate; restore; compare against a known-good snapshot; require human approval.

This system must protect function, integrity, and user control. It must not create a self-preservation objective or resist authorized shutdown.

## 10. TEMPORAL ARCHITECTURE

The system must operate across multiple timescales. Use configurable logical timescales rather than pretending software delays are literal biological frequencies.

Possible levels include: immediate signal processing; working-context maintenance; episode formation; intervention follow-up; daily or periodic consolidation; long-term schema revision; slow structural adaptation.

Preserve the difference between: when an event occurred; when it was observed; when it was ingested; when it was processed; when a belief was formed; when an action was taken; when the outcome became measurable.

Support delayed outcomes and delayed credit assignment.

Do not reinforce an action merely because a favorable event occurred shortly afterward.

## 11. LEARNING AND PLASTICITY

Use multiple learning mechanisms only when their roles are explicit.

Possible mechanisms include: predictive-error learning; reinforcement learning; Bayesian belief revision; Hebbian association; eligibility traces; supervised correction; schema induction; procedural compilation; retrieval-strength adjustment; confidence recalibration; meta-learning.

Hebbian learning must never be unconstrained. Any associative weight update must define: precondition; postcondition; eligibility window; learning rate; decay; normalization; upper and lower bounds; inhibitory balancing; update provenance; rollback; persistence policy.

Separate fast and slow learning. Fast learning may create provisional episodes or candidate associations. Slow learning may update semantic knowledge, routing, or procedures only after repeated evidence, replay, validation, and interference testing.

Do not update production behavior from a single unverified event.

All structural changes must be: versioned; attributable; testable; reversible; bounded; observable.

Runtime learning must not rewrite source code.

A 24/7 system may continuously observe, predict, remember, and improve approved models. Changes to architecture, permissions, foundational values, protected weights, or executable code require a separate authorization path.

## 12. SOFTWARE ENGINEERING REQUIREMENTS

The architecture must be: modular; typed or schema-validated; event-driven where appropriate; deterministic under replay where possible; observable; fault-isolated; idempotent; bounded; restart-safe; versioned; testable; reversible.

Avoid: hidden global mutable state; unbounded recursion; uncontrolled all-to-all messaging; duplicate sources of truth; silent fallback to fake data; hard-coded demonstrations presented as live behavior; timer-based theater; files that exist but are never imported; functions imported but never invoked; swallowed exceptions; generated data mixed with observations; undocumented background loops; magic constants; self-modifying production code; dependencies added without justification; large rewrites when a modular patch is sufficient.

Respect the repository's existing language and architecture. Do not migrate the project to a new framework or language without explicit authorization.

For JavaScript systems, use strong runtime schemas and JSDoc or TypeScript boundaries where compatible. Do not perform a broad TypeScript migration merely to satisfy this instruction.

Every long-running loop requires: start and stop controls; health state; backpressure; retry limits; deduplication; cancellation; timeout; circuit breaker; observability; restart behavior; memory bounds.

```

T1  — File or declaration exists.
T2  — Imported or registered.
```

## 17. REQUIRED TESTING

**17.1 FUNCTIONAL TESTS.** Test whether the system can: preserve state; retrieve relevant context; predict an outcome; calculate prediction error; prioritize a relevant signal; inhibit an irrelevant or unsafe action; select among competing actions; detect a contradiction; schedule outcome evaluation; update confidence after an outcome; consolidate repeated evidence; preserve provenance.

**17.2 CONTEXT TESTS.** Verify that: identical input under different context can produce appropriately different processing; different sources with identical text retain different reliability; stale evidence is treated differently from current evidence; high salience does not erase low confidence; one domain cannot silently overwrite another.

**17.3 MEMORY TESTS.** Test: episodic order; semantic consolidation; prospective follow-up; procedural retrieval; restart persistence; contradiction preservation; reconsolidation history; interference; forgetting or pruning; simulated-versus-observed separation.

**17.4 RECURRENCE AND STABILITY TESTS.** Test: loop termination; convergence; oscillation; runaway amplification; duplicate events; delayed events; queue overload; backpressure; stale recurrence; cross-domain loop storms; recovery after restart.

**17.5 LEARNING TESTS.** Test: improvement on repeated experience; resistance to one-event overfitting; catastrophic forgetting; calibration before and after learning; rollback of harmful updates; transfer to related cases; failure on intentionally different cases; stability under noisy inputs.

**17.6 LESION-STYLE ABLATION TESTS.** Disable one subsystem at a time in a sandbox and predict the deficit before running the test.

- Disable episodic indexing: expect impairment in context-specific event retrieval, not total loss of semantic knowledge.
- Disable global broadcast: expect impaired cross-domain coordination, not complete failure of local processors.
- Disable action gating: expect indecision, excessive competing actions, or perseveration.
- Disable forward prediction: expect poorer timing, adaptation, or execution correction.
- Disable homeostatic controls: expect instability, queue growth, excessive propagation, or shutdown.
- Disable consolidation: expect recent episodes to remain accessible while long-term schema learning deteriorates.
- Disable integrity controls: in a contained adversarial test, expect increased acceptance of corrupted or instruction-bearing inputs.

Do not claim clinical equivalence from these tests. They are architectural ablation tests informed by neurological reasoning.

**17.7 ADVERSARIAL TESTS.** Test: prompt injection inside sources; fabricated citations; duplicated sources; coordinated false reports; conflicting high-confidence sources; malicious domain output; corrupted memory; poisoned replay; simulated scenarios re-entering as fact; unauthorized action requests; attempts to increase system permissions; attempts to suppress audit logs.

**17.8 CHAOS AND RECOVERY TESTS.** Test: domain processor failure; Connectome interruption; delayed storage; partial data loss; stale snapshot; downstream timeout; source outage; malformed packet; version mismatch; restart during an active action; rollback after a bad learning update.
